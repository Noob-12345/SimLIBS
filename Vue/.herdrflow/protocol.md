# 协作与交接协议 v0.1

## 两个生命周期

团队初始化：initialized → initializing → ready。ready 表示角色已确认职责，不表示任务完成。身份变化、缺少确认、授权提示或未确定的操作都不能被当作 ready。

业务任务：planned → implementing → awaiting_review → reviewing → accepted → completed。
需要修复时：reviewing → changes_requested → implementing。任意阶段可进入 blocked，记录原因及恢复前阶段。

第一版的脚本管理团队初始化；业务任务由协调 agent 按此协议推进，尚无自动任务状态机。

## 分派要求

每次分派包含 taskId、唯一 dispatchId、revision、负责人、目标、验收标准、输入资料、允许和禁止修改范围、验证命令与交付路径。首次任务前补全模板；不发送只有“开始开发”的指令。

返工增加 revision 并生成新的 dispatchId。归档上一轮报告，不能让旧完成标记或旧报告推进当前任务。Herdr idle/done 只描述终端状态；完成以对应分派的报告和可核验证据为准。

## 修改与审查

共享目录只允许一名实现者写业务代码。实现者交付后冻结变更；审查者与协调者只读检查。构建和会改写文件的测试串行运行，避免产物相互干扰。

审查对象记录提交 SHA；有未提交变更时，还需记录 diff 和相关文件哈希（包括未跟踪文件），不能只用 HEAD 代表实际改动。审查之后有代码变化，就重新确认受影响范围。

审查结果由协调者核实并合并为一份返工说明。达到 config.maxFixRounds 后，协调者说明未解决问题和原因，决定重新拆分、调整方案或请求必要决策，不能无限重复同一轮。

## 交付与权限

实现报告记录实际验证命令与结果；审查报告给出位置、依据与影响；验收报告逐条对照验收标准给出证据。

角色约束是协作协议，不等于操作系统只读权限。保持 agent 原有权限与用户授权，不通过启动参数自动绕过授权。完成工作流不自动触发提交、推送、合并或发布。

## 持久化与恢复

配置、职责与任务记录存于项目 `.herdrflow/`。state.json 和 runtime/ 属于本机运行状态，默认忽略；config、roles、protocol、templates 和合适的任务记录可版本管理。

协调者单写团队状态和 task.json；各角色仅写自己的报告和 ready 确认文件。就绪确认绑定 runId、角色、pane、terminal、随机 token 和职责/配置指纹；仍需协调者阅读确认内容判断是否理解正确。

恢复前重新发现真实资源，读取当前任务和最后交接，不直接重放最后一条修改指令。初始化脚本对不确定的 split、启动或提示提交保留证据；先检查是否已经发生，再决定重试。

存在活动任务时，不得让第二个实现者在同一目录接管，直到确认旧写入者已停止并明确交接。第一版不自动迁移丢失或被替换的 pane，也不提供自动 worktree 集成。
